# Instalar primero los MCP de Espressif, no paquetes comunitarios

Para Órbita (ESP32-S3, ESP-IDF, Windows), lo único con respaldo de un fabricante son dos servidores MCP de Espressif: uno de documentación remoto (`mcp.espressif.com/docs`) y uno local de herramientas (`idf.py mcp-server`, solo desde ESP-IDF v6.0). Todo lo demás (skills, plugins, agentes y MCP de serie, depuración o KiCad) es comunitario, de madurez baja o media, y casi nada cubre el dominio real del proyecto (I2S, AFE, PSRAM, DMA). Anthropic no ofrece nada específico de embebidos. El ecosistema de skills embebidas se describe como escaso, y una investigación citada por Snyk halló prompt injection en 36% de las skills probadas ([Snyk](https://snyk.io/articles/claude-skills-embedded-systems-engineers/)). Los agentes, skills y hooks propios del proyecto ya siguen las buenas prácticas recomendadas (revisores de solo lectura, skills versionadas). La mejora de mayor valor es agregar el MCP de docs de Espressif, una verificación de build al terminar y dos skills propias, no sumar paquetes ajenos. Ninguna herramienta fue probada: todo viene de lectura de documentación y READMEs, y no hay evidencia verificable de uso en Windows con ESP32-S3.

## Espressif ofrece dos MCP oficiales y una barrera: ESP-IDF 6.0

El MCP de documentación es remoto, se instala con `claude mcp add --transport http espressif-docs https://mcp.espressif.com/docs` y luego `/mcp` y Authenticate (login GitHub o WeChat). Expone una sola herramienta de búsqueda semántica sobre datasheets, TRM, hardware design guidelines y la guía de programación de ESP-IDF. Solo cubre documentación pública de la última versión, con **límites de 40 solicitudes por hora y 200 por día** ([blog Espressif](https://developer.espressif.com/blog/2026/04/doc-mcp-server/)). No se confirmó si cubre ESP-SR o ESP-DSP, que es justo lo que usa el frente Audio. El MCP local `idf.py mcp-server` ofrece `set_target`, `build_project`, `flash_project` y `clean_project`, más recursos de estado. Exige **ESP-IDF v6.0 o superior y EIM 0.8.1 o superior**, y se instala con `claude mcp add --transport stdio esp-idf-eim -- eim run "idf.py mcp-server"`, ejecutado desde un proyecto ESP-IDF válido ([blog Espressif](https://developer.espressif.com/blog/2026/04/esp-idf-tools-mcp-server/)). El blog no documenta Windows ni expone monitor serie. Sin migrar a v6.0 este servidor no existe para el equipo, y desde Claude Code basta con ejecutar `idf.py build` y `flash` por terminal, que ya cubre lo mismo. No se verificó qué versión de ESP-IDF usa el equipo. La migración de 5.x a 6.0 tiene una skill comunitaria (`esp-idf-v6-migration`), pero conviene migrar por razones propias del proyecto y no solo por este MCP.

Espressif tampoco publica un plugin de Claude Code para ESP-IDF. Su workshop oficial "AI agent coding for ESP-IDF" (ESP-IDF v6.0.2, probado con ESP32-C5) enseña a conectar el MCP de docs, agregar skills y usar flujo spec-driven con depuración basada en evidencia del dispositivo, pero las skills que instala vienen de un mantenedor individual ([workshop](https://developer.espressif.com/workshops/ai-agent-coding-for-esp-idf/)). Es una buena guía de método para el equipo.

## El ecosistema comunitario es delgado y exige leer el código antes de instalar

Las skills ESP-IDF existentes son de madurez baja. `adamlipecz/esp32-firmware-engineer-skill` es la más completa (references de RTOS, sdkconfig, particiones, OTA y triage de panic logs, scripts de build y flash), pero tiene **12 estrellas y 7 commits** ([GitHub](https://github.com/adamlipecz/esp32-firmware-engineer-skill)). `pedrominatel/awesome-esp-ai` aporta las skills `esp-idf`, `esp-idf-v6-migration` y `esp-idf-components`, con 9 estrellas y afiliación a Espressif no declarada ([GitHub](https://github.com/pedrominatel/awesome-esp-ai)). Las colecciones grandes (Jeffallan, 11.9k estrellas; VoltAgent, unas 25.7k) solo traen entradas genéricas de embebidos, y la skill de Cortex-M de antigravity no aplica a Xtensa ([Jeffallan](https://github.com/Jeffallan/claude-skills), [VoltAgent](https://github.com/VoltAgent/awesome-claude-code-subagents), [Snyk](https://snyk.io/articles/claude-skills-embedded-systems-engineers/)). El agente `embedded-systems` de VoltAgent, según un resumen de búsqueda, incluye herramientas Write y Edit, lo opuesto a los revisores de solo lectura del proyecto, y no se leyó su archivo. No se encontró ninguna skill de I2S/audio, AEC/AFE, ni de revisión de ISR/DMA en ESP32 (búsqueda negativa, no exhaustiva). Se descarta instalar paquetes completos por solapamiento con los agentes propios, herramientas de escritura y riesgo de supply chain; si algo sirve, se copian fragmentos tras leerlos.

En MCP comunitarios, la brecha real en Windows es el monitor serie. `es617/serial-mcp-server` (24 estrellas, MIT, pyserial) es el candidato más seguro; su README advierte que los plugins ejecutan Python con todos los privilegios y que no se use "always allow" ([README](https://raw.githubusercontent.com/es617/serial-mcp-server/main/README.md)). `cmd0s/esp32-ai-loop-mcp-server` (9 estrellas) agrega monitor, tail y grep de logs, pero declara que el reset puede comportarse distinto con el USB-Serial/JTAG del S3, que es el que usa Órbita ([README](https://raw.githubusercontent.com/cmd0s/esp32-ai-loop-mcp-server/main/README.md)). `jinw06k/esp-idf-monitor-mcp` no sirve en Windows (monitor requiere PTY) y obliga a sobrescribir un archivo de la instalación de ESP-IDF ([README](https://raw.githubusercontent.com/jinw06k/esp-idf-monitor-mcp/main/README.md)). `horw/esp-mcp` se autodeclara prueba de concepto, no tiene licencia listada y quedó superado por el oficial ([README](https://raw.githubusercontent.com/horw/esp-mcp/main/README.md)). En depuración, `embedded-debugger-mcp` (201 estrellas) soporta Xtensa solo por OpenOCD experimental y con registros mal numerados (PC y SP incorrectos), y su análisis de fallas es solo Cortex-M ([README](https://raw.githubusercontent.com/Adancurusul/embedded-debugger-mcp/main/README.md)); para un S3 es prematuro. El MCP de Saleae Logic 2 es oficial aunque experimental ([docs Saleae](https://docs.saleae.com/mcp/guides/getting-started)), y solo aplica si el equipo tiene el analizador. Un criterio práctico: con menos de unas 30 estrellas son proyectos de una persona, útiles para probar, riesgosos para depender de ellos.

## El lado PCB: la IA es segunda opinión, y todavía no hay PCB

Existen MCP de KiCad (el más maduro, `mixelpixx/KiCAD-MCP-Server`, unas 2.7k estrellas, ya anuncia migración a otro proyecto llamado Konnect; `lamaalrajih/kicad-mcp`, 526 estrellas, orientado a análisis) y servidores de partes JLCPCB sin API key ([mixelpixx](https://github.com/mixelpixx/KiCAD-MCP-Server), [lamaalrajih](https://github.com/lamaalrajih/kicad-mcp)). Todos son comunitarios y requieren KiCad 9 o superior. Para Digi-Key y Mouser hay servidores pequeños que piden credenciales propias de API. Como hoy no hay proyecto KiCad, solo vale mirar los de partes (elegir partes "Basic" de JLCPCB evita el cargo por parte extendida de unos USD 3 por parte única, según el README de `jlc-mcp`, cuya procedencia no pudo verificarse porque el repo citado dio 404) ([README jlc-mcp](https://cdn.jsdelivr.net/npm/@jlcpcb/mcp@0.4.0/README.md)). Los MCP de KiCad conviene esperarlos hasta tener esquemático.

Sobre confiabilidad, los sistemas serios de revisión de esquemáticos con LLM (DRCY, de AllSpice) no confían en el modelo solo: combinan recuperación de datasheet, consenso entre varias corridas y verificación determinista, y no publican métricas de exactitud en el abstract ([arXiv 2603.15672](https://arxiv.org/abs/2603.15672)). Tampoco se hallaron cifras de alucinación de pines para Claude. Los datos del ESP32-S3 que un LLM puede mezclar son concretos: GPIO45 define VDD_SPI, GPIO19/20 tienen glitches de unos 60 µs al arrancar y GPIO33–37 quedan inutilizables con PSRAM octal ([Schematic Checklist](https://docs.espressif.com/projects/esp-hardware-design-guidelines/en/latest/esp32s3/schematic-checklist.html)). El flujo recomendado es el checklist de Espressif, luego ERC/DRC de KiCad, la IA como segundo par de ojos citando página y tabla del datasheet, y revisión humana externa antes de fabricar. Los puntos de riesgo propios del proyecto (5 V para el amplificador clase D, ruteo de referencia AEC, interfaz NFC, SD por SPI) no están cubiertos por ninguna fuente leída. Sheetsdata (MCP de datasheets, de pago por créditos, precisión sin auditar) no se recomienda: el MCP de docs de Espressif ya cubre el chip.

## Verificación: claro valor en lógica pura, poco en audio

Para análisis estático, lo oficial es `idf.py clang-check`, documentado como "still under development", que requiere `IDF_TOOLCHAIN=clang` y `esp-clang` ([doc ESP-IDF](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32s3/api-guides/tools/idf-clang-tidy.html)); cppcheck funciona de forma genérica sobre `compile_commands.json` y MISRA sería sobredimensionado. `-fanalyzer` es ruidoso y apto solo para C ([GCC wiki](https://gcc.gnu.org/wiki/StaticAnalyzer)). Ninguna de estas herramientas modela carreras entre tarea e ISR ni coherencia de caché DMA/PSRAM (no se halló fuente que diga lo contrario), así que esa revisión sigue en `embedded-reviewer` y en pruebas en placa. Wokwi simula el S3 con PSRAM y WiFi, pero **I2S no está implementado en el S3**, de modo que no sirve para micrófonos ni AFE; sí para FSM y WebSocket, con 50 minutos gratuitos de CI por ventana de 30 días ([Wokwi ESP32](https://docs.wokwi.com/guides/esp32), [Wokwi CI](https://docs.wokwi.com/wokwi-ci/getting-started)). QEMU de Espressif tiene binarios para Windows, pero no lista qué periféricos del S3 emula ([doc QEMU](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32s3/api-guides/tools/qemu.html)). El target `linux` es experimental y está documentado solo para Linux y macOS ([Host apps](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32s3/api-guides/host-apps.html)), por lo que en Windows implica WSL2. La inferencia más útil: aislar ring buffer, framing y FSM en un componente C sin includes de `driver/` ni FreeRTOS y probarlo en host con Unity. Para depuración automatizable, `idf.py size-components --format json`, core dump por UART con `idf.py coredump-info` y heap tracing producen texto legible por un agente ([idf.py](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32s3/api-guides/tools/idf-py.html), [Core dump](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32s3/api-guides/core_dump.html), [Heap](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32s3/api-reference/system/heap_debug.html)). Build, flash y monitor deben quedarse en Windows nativo; WSL2 con usbipd agrega fricción, y el CI en GitHub Actions (`espressif/esp-idf-ci-action@v1`, con `target: esp32s3`) da feedback sin instalar nada local ([action](https://github.com/espressif/esp-idf-ci-action)).

## Recomendación priorizada para Órbita

Los puntos 1 a 6 son inferencias nuestras a partir de las fuentes, no hallazgos citados; las fuentes respaldan la existencia y el método de cada herramienta, no su efectividad en este proyecto.

| Prioridad | Acción | Costo / riesgo |
|---|---|---|
| Instalar ya | 1. MCP de docs de Espressif (comando arriba); que `embedded-reviewer` y `pin-map-check` citen datasheet o guideline en vez de memoria. Probar primero si cubre ESP-SR/AFE. | Bajo; límite de 40 solicitudes por hora. |
| Instalar ya | 2. Hook `Stop` o `TaskCompleted` que corra `idf.py build` y bloquee con exit 2 si falla; medir que el tiempo sea tolerable en Windows 10. | Medio; el build completo puede ser lento. |
| Instalar ya | 3. Extender el hook de edición existente para bloquear cambios a `sdkconfig` generado, `build/` y `managed_components/`. | Bajo. |
| Instalar ya | 4. Skill propia `audio-pipeline-check` (16 kHz/16-bit, PSRAM vs DMA interno, alineación DMA, chunks I2S, presupuesto de RAM/CPU del AFE), con `references/` como patrón de Beningo. | Escribirla es trabajo del equipo; nada comunitario la cubre. |
| Instalar ya | 5. Skill propia `panic-triage`, tomando de referencia las references de adamlipecz (leídas, no instaladas). | Bajo. |
| Instalar ya | 6. Línea en CLAUDE.md: citar sección o tabla del datasheet al afirmar un pin o registro; errata del S3 es zona de verificación manual. | Mínimo. |
| Esperar | MCP de ESP-IDF Tools (hasta migrar a v6.0; mientras tanto, `idf.py` por Bash). MCP serie (`es617/serial-mcp-server`) solo si los logs por Bash resultan incómodos. MCP de KiCad y de partes JLCPCB cuando exista proyecto de PCB. Saleae solo si tienen el hardware. | Verificar Windows, versión de IDF y estado de mantenimiento. |
| Esperar | Tests host con Unity sobre lógica pura, `clang-check` y cppcheck cuando la FSM y el framing estén estables; Wokwi solo para FSM/WebSocket. | Medio; clang-check en Windows no verificado. |
| Evitar | Instalar colecciones completas (Jeffallan, VoltAgent, wshobson, antigravity), `horw/esp-mcp`, el addon de monitor de jinw06k (Windows), MCP de depuración OpenOCD/GDB para Xtensa, Sheetsdata, WSL2 para flashear, MISRA completo, "always allow" en cualquier MCP que flashee o escriba al puerto serie. | Supply chain, solapamiento, inmadurez. |

Reglas de higiene comunes: leer SKILL.md, scripts y `allowed-tools` antes de copiar cualquier cosa de terceros; mantener aprobación manual para cada flasheo; y reglas de hooks que dependan de garantías duras deben ir en el sistema de permisos, porque el filtro `if` de los hooks es best-effort ([docs de hooks](https://code.claude.com/docs/en/hooks)).

## Lo no verificado

No se probó ninguna herramienta. No se conocen las fechas de último commit de ningún repo ni la versión de ESP-IDF del equipo. Tampoco se verificó la estabilidad de `idf.py mcp-server` en Windows, la cobertura de ESP-SR/AFE del MCP de docs, la existencia de un repo oficial de Espressif con skills (solo se hizo búsqueda general), `clangd-lsp` u otros plugins en el marketplace oficial de Anthropic (`anthropics/claude-plugins-official`, 37.8k estrellas, cuya página no lista plugins individuales), el contenido de las skills de Jeffallan y VoltAgent, `clang-check` ni `wokwi-cli` en Windows, qué emula QEMU del S3, ni MCP para PCBWay, ensamblado SMT o DFM. El modo del hook `Stop` con builds largos y el soporte de hooks bash en Windows (se asume Git Bash, porque el proyecto ya usa `.sh`) quedan por medir. La ruta del repo bajo OneDrive puede chocar con la restricción de rutas del instalador de ESP-IDF (máximo 90 caracteres, sin espacios), según las notas previas del proyecto. Los conteos de instalaciones y estrellas de agregadores (Glama, claudemarketplaces, Snyk) pueden estar desactualizados.

## Conclusión

La conclusión incómoda es que, para este dominio, casi no hay nada que instalar: la ventaja está en conectar el conocimiento oficial de Espressif al flujo que el equipo ya construyó, en cerrar el lazo de build con hooks y en escribir las dos skills que nadie publicó (audio/DMA/PSRAM y triage de panic). Las herramientas de IA para PCB y depuración con OpenOCD/GDB son demasiado inmaduras o prematuras para un S3 sin placa final, y conviene revisarlas de nuevo cuando exista esquemático y cuando ESP-IDF 6.0 esté adoptado.
